# Приоритеты сводного дашборда

Реализация и уточнения периодов выпущены 17.09.2026 в BLUE `3c3dc4ac…`, generation9,
по отдельному плануed4. Реальный публичный интерфейс и API проверены; [production checkpoint](deployment/dashboard-periods-production-2026-09-17.md)
содержит точные receipts и ограничения данных. Ниже описаны возможные сигналы:
они появляются только при выполнении условий и достаточном подтверждении фактов.

## Что видит руководитель

### Недельный период — выпущено 17.09.2026

По уточнению пользователя `full-week` означает последние **7 завершённых суток**,
заканчивающиеся вчера. Он остаётся периодом по умолчанию для `/dashboard`;
подпись фильтра — «Последние 7 дней», на узком экране — «7 дней».
На 17.09.2026 выбранный диапазон — **10–16.09.2026**, сравнение — **03–09.09.2026**.
График сводки получает семь последовательных дневных значений из той же выборки,
что карточки, результаты клубов, ассортиментные сигналы и детализация.

Общий resolver применяется также к ассортименту: одинаковый `full-week` имеет
одинаковые границы. `week` по-прежнему означает текущую календарную неделю;
остальные периоды, правила бизнес-дат/таймзон, доступ клубов и `asOf` не меняются.
Границы периода не сдвигаются к последнему загруженному факту: отсутствующий день
остаётся отсутствующим, подтверждённый ноль — нулём. Изменение опубликовано
в BLUE `3c3dc4ac…`, generation9, и подтверждено на production API и в браузере.

Проверено локально: 40 тестов DashboardService, сборки API/Web и линтеры
изменённых файлов. В Chromium актуальный скомпилированный API на синтетических
сохранённых фактах выдаёт семь точек 10–16.09 и сравнение 03–09.09; проверены
последняя точка/tooltip, переход к детализации, применение и перезагрузка фильтра,
экраны 1440/390px и светлая/тёмная тема. Это не проверка нового кода в production.

### Суточные итоги и история за 21 день — выпущено 17.09.2026

При `full-day` карточки, результаты клубов и приоритеты сохраняют выбранные
полные сутки и их сравнение с предыдущими сутками. График отдельно запрашивает
последние **21 завершённый день**, заканчивающиеся выбранными сутками. На
17.09.2026 это **27.08–16.09**, тогда как KPI относятся только к **16.09**.
Заголовок «Динамика за 21 день» показывает свой диапазон и дату суточных итогов.
Если сравнение включено, пунктир сопоставляет предыдущие 21 день (**06–26.08**);
обе даты подписаны у графика. Суточное сравнение KPI остаётся **16.09 к 15.09**.

История использует существующий read-only `executive-summary` с `period=custom`
и принятыми клубами, их таймзонами и `asOf`. Запрос ограничен 15 секундами и идёт
параллельно ассортиментным сигналам. Выбор карточки переключает уже загруженный
ряд без новых запросов. `summary.days` дневного отчёта остаётся однодневным;
отдельная история передаётся только графику. Его детализация открывает 21 день,
а возврат восстанавливает `full-day` и выбранные клубы.

Ответ с другим scope или неполной/переставленной осью отвергается. При сбое
истории суточные итоги остаются доступны, а график показывает ошибку загрузки;
однодневный результат не используется вместо истории. Неподтверждённые дни
сохраняют `null` и разрывы, известный ноль остаётся нулём. Недельный режим
сохраняет последние семь завершённых дней; прочие периоды не расширяются.

Проверка изменения: 17 Web-тестов (14 для истории и 3 для правил приоритетов),
targeted lint и сборка Web прошли. Тесты включены в Fast CI и Release admission CI
через `test:executive-dashboard`. Локальный Chromium с фактическим API service
и синтетическими сохранёнными фактами подтвердил отдельные суточные итоги и
21 точку истории, значения трёх tooltip, переход/возврат, смену клубов,
сравнение, отсутствие новых запросов при выборе KPI, пропуски и сбой истории.
Проверены 1440/390px и обе темы. Эти локальные проверки дополнены реальной
восстановленной копией обоих слотов, native68/resource/cooldown и production
API/public browser 17.09.2026. Точные receipts и ограничения приведены в checkpoint.

В `/dashboard` сохранены пять основных карточек и переключение графика нажатием на карточку. Средний товарный чек добавлен в расчёты и детализацию, но не стал шестой карточкой.

«Приоритеты» показывает три первых действия и общее число сигналов. «Все приоритеты» раскрывает список с прокруткой: большой список не растягивает график. Порядок: просроченные обязательства и отсутствие товара; подтверждённое снижение финансовых показателей/визитов; обучение, проверка, ближайший запас и товары без продаж; качество данных. Это порядок действий, а не оценка потенциальной прибыли.

| Сигнал | Условие | Куда ведёт |
| --- | --- | --- |
| Снижение среднего товарного чека | Текущий и предыдущий средний чек подтверждены, абсолютное изменение меньше нуля | Средний чек по клубам и дням, основания расчёта |
| Снижение дохода на визит | Оба периода имеют совместимые подтверждённые выручку и визиты, изменение меньше нуля | Доход на визит по клубам и дням |
| Просроченные задачи | `dueAt < serverNow`, статус не `DONE/CANCELED` | Точный текущий список, затем `taskId` |
| Просроченные чек-листы | `scheduledAt < serverNow`, статус `OPEN/IN_PROGRESS/RETURNED/ESCALATED` | Список незавершённых запусков, затем `runId` |
| Сданные чек-листы ждут проверки | `ON_REVIEW` после планового срока выполнения | Отдельная очередь проверки; срок проверки/SLA не придуман |
| Не завершено обязательное обучение | Активный сотрудник имеет назначенный обязательный курс, статус не `COMPLETED/WAIVED` | Сотрудники и конкретные курсы, затем профиль по `userId` |
| Не подтверждены регламенты | У активного сотрудника нет ознакомления с текущей опубликованной версией назначенного регламента | Сотрудник, название и версия; отдельная ссылка в каталог |
| Нет в наличии | Положительный canonical OOS counter с допустимым состоянием источника и метрики | OOS с теми же клубами и cutoff |
| Запас менее трёх дней | Положительный canonical low-stock counter | Соответствующий список OOS/low-stock |
| Без продаж 21 день | Положительный canonical no-sales counter | Отчёт без продаж, окно 21 день |
| Снижение визитов | Подтверждённое сопоставимое снижение | Детализация визитов |
| Неполная выручка | Главная выручка не `AVAILABLE` | Причина и основания расчёта |

Только положительное число создаёт операционный сигнал. Подтверждённый ноль не создаёт предупреждение. Недоступность не означает «проблем нет»: состояние проверки доступно в свёрнутой строке источников. `PARTIAL` показывается как «не менее», `STALE/MISSING/FAILED` не подтверждают текущий товарный риск. Каждый список читается заново и может измениться после завершения задачи или обновления фактов.

## Два разных финансовых показателя

**Средний товарный чек** = выручка подтверждённых товарных чеков / число чеков. Одна операция или строка товара не становится чеком без сохранённого идентификатора. Namespace: provider + domain + Store + receipt identity. Отменённые операции исключаются. Идентификатор, повторившийся в разных fiscal days проверяемого предыдущего и текущего окна, исключается как неоднозначный. Переключение сравнения не меняет допуск текущих чеков.

Число чеков, покрытие операций и покрытие выручки передаются отдельно в `receiptEvidence`. В расчёт допускаются только подтверждённые store-days. `AVAILABLE` требует полного покрытия дней и операций; подтверждённая часть имеет `PARTIAL`. Пустой период даёт `value=null`, а настоящий бесплатный чек может дать `value=0`. При нулевой/отрицательной денежной базе процент покрытия не выдумывается. Итог периода и сети считается по всем допущенным чекам, не усреднением дневных или клубных средних.

**Доход на визит** = выручка оказанных услуг и товаров / подтверждённые визиты той же выборки. Пополнения баланса остаются отдельно. В текущем API нет независимого полного доказательства услуг и полноты визитов: этот показатель остаётся `MISSING`; сигнал снижения подключён и появится только при подтверждённых основаниях. Частичная товарная выручка, делённая на наблюдавшиеся сессии, не подменяет его.

Оба сигнала используют сравнение, рассчитанное API. Отключённое сравнение, отсутствующий прошлый период, `PARTIAL` и нечисловые значения не создают снижение. Старый API без `averageProductCheck` отображается без ошибки и без ложного нуля.

## Персонал: текущее состояние и доступ

- `GET /staff/operations-dashboard/priorities` возвращает текущие счётчики и `evaluatedAt`.
- `GET /staff/operations-dashboard/priorities/items?kind=...` возвращает список того же kind/scope, страницы по 20, максимум 100. Cursor связан с tenant, пользователем, kind и принятой выборкой клубов через компактный SHA-256 fingerprint; длинная выборка не раздувает cursor. Смена выборки требует новой первой страницы.
- Financial `dateFrom/dateTo/asOf` не применяются к персоналу. `evaluatedAt` задаёт сервер, клиент не переносит часы проверки в прошлое.
- Сохраняются corporate JWT, RolesGuard и transitional `FreshNetworkScopeGuard`. В reader дополнительно проверяется fresh scope и каждый запрошенный Store. STORES-доступ не превращается в NETWORK ради сводки.
- Нужен `view_staff_control` и право исходного раздела: задачи — `view_staff_tasks`, чек-листы — `view_staff_standards`. Межсотрудниковые учебные показатели требуют `view_staff_training` + `manage_staff_training`; регламенты дополнительно требуют стандартов. Self-only профиль не используется вместо сетевого отчёта.
- По умолчанию выбираются активные клубы. Общесетевые задачи и сотрудники NETWORK без привязок включаются только при выборе всей активной сети. Они не приписываются произвольному клубу. Явно запрошенный доступный неактивный клуб не добавляет остальные неактивные клубы.
- Сотрудники должны быть активны; курсы и регламенты сохраняют канонические правила роли и назначения. Многоклубный сотрудник учитывается один раз. Материалы другого клуба не попадают в его выбранную выборку.
- Задачи и чек-листы используют отдельный `count`, без legacy cap 5000. Details используют тот же predicate и стабильную пагинацию по id. Это текущая очередь, не исторический snapshot между запросами.
- Учебные отчёты пока ограничены 300 сотрудниками и 400 курсами/регламентами. Прогресс и ознакомления для допущенных материалов читаются без ограничения истории. Поэтому положительные выявленные пробелы достоверны, но итог при достижении лимита — только нижняя граница. Ноль при ограниченном списке остаётся неизвестным. Некорректная привязка сотрудника также обозначается в coverage.
- Оценки/аттестации и знания из knowledge-base не подменяются статусом обязательного курса. Их самостоятельные сигналы перечислены ниже как следующая работа.

Reader зарегистрирован в существующем StaffModule. DashboardModule не импортирует большой граф Staff/Integrations. GET не назначает обучение, не создаёт задачи/запуски, не подтверждает ознакомление и не отправляет уведомления.

Web запускает отдельный staff request после получения accepted summary и передаёт результат через Suspense slot. Медленный или недоступный персонал не задерживает показ основных KPI и бизнес-сигналов. Ответ с другой выборкой клубов отклоняется. Старый endpoint/403/timeout показывают ограничение, без обходного запроса широкого legacy отчёта.

## Проверка остальных блоков и следующий приоритет

| Блок | Что ещё важно | Решение по текущей доработке |
| --- | --- | --- |
| Финансы и посещаемость | Полнота игровых услуг, подтверждение визитов и реальных пополнений | Не придумывать коэффициенты. Следующий этап — доказать источники; после этого заработает сравнение дохода на визит |
| Ассортимент | Избыточный запас, деньги в нём, списания, отрицательная/снижающаяся маржа | OOS/low-stock/no-sales уже включены. Дополнительные денежные предупреждения требуют свежего cost basis, сопоставимости и согласованных порогов |
| Персонал | Не сданные/просроченные аттестации, истёкшие допуски | Следующий самостоятельный сигнал из readiness/assessment evidence. История assessment сейчас ограничена; нельзя трактовать её отсутствие как доказанный провал |
| Контроль смен и кассы | Возвраты, отсутствие инкассации, непривязанный оператор, аномально длинные смены | Сначала согласовать определения и пороги по клубам; не объявлять любой возврат нарушением |
| CRM и маркетинг | Просроченные обещания гостям и задачи кампаний | У `GuestCrmTask` есть dueAt, но нет Store. Для сети возможен отдельный сигнал, для поднабора клубов нужна доказанная привязка. Кампания со связанной CRM-задачей не должна дублировать предупреждение |
| Поддержка | Обращения без ответа и критические обращения | У тикетов есть Store/статус/lastActivityAt, но нет dueAt/приоритета/SLA. Нужны правила срочности; обычная очередь NEW не становится аварией |
| Интеграции | Неуспешное обновление или устаревший снимок конкретного источника | Есть read-only BusinessSnapshot status. Следующий отдельный сигнал с freshness и scope, без кнопки автоматического sync из сводки |
| Игровые награды | Неоднозначная выплата, FAILED, долгое ожидание | Требуется отдельная безопасная агрегированная проекция; RECONCILIATION_REQUIRED сейчас входит в общий processing status. Сводка не запускает replay/retry и не пересекает worker boundary |
| Коммуникации и администрирование | Непрочитанные сообщения, доступы, состояние tenant | Не смешивать непрочитанность со срочностью; не включать межтенантовые platform данные в сводку сети |

## Проверки и файлы

### Исходная доработка производительности, 16.09.2026

Месячная сводка повторно использовала одну выборку сессий для сети, клубов и
каждого дня текущего и предыдущего периода. Привязка сессии и её локальный день
теперь вычисляются один раз в рамках запроса; форматтер времени переиспользуется
для каждого часового пояса. Между запросами и сетями эти результаты не сохраняются.
Проверки клубов, неоднозначной привязки, границ локальных дней, уникальности сессий,
`factAsOf` и состояний `PARTIAL/MISSING` сохранены. Раннего фильтра SQL только по
`storeId`, который потерял бы старые непривязанные сессии, нет.

Проверка на изолированной копии для предыдущего кандидата a8 дошла до первого
тяжёлого запроса месячной сводки и остановилась на HTTP-ошибке. Переполнения памяти
и перезапусков не наблюдалось; точный тип исключения прежний тест не сохранял.
Новый тестовый клиент записывает только безопасные фазу, код ошибки, статус,
размер и длительность запроса в отдельный файл сбоя. Ограничения 20 секунд на
ожидание сокета, 16 МиБ ответа и обязательная остановка тестовых приложений
сохранены. Эта запись описывает исходный код; успешная проверка нового артефакта
и production-выпуск ещё требуются.

API: `common/receipt-metrics.ts`, `dashboard/dashboard.service.ts`, `staff/staff-priorities.service.ts`, contract и контроллер. Web: `executive-dashboard.tsx`, `staff-priorities.ts`, `staff-priorities-types.ts`, `executive-priority-rules.ts`, `/dashboard/priorities` и `/dashboard/executive-details`.

Локально пройдены полный API набор 194 suites / 3588 tests (2 прежних TODO), 17 PostgreSQL integration scenarios, Web typecheck/build, отдельные правила финансового сравнения и browser fixture scenarios. PostgreSQL fixture — только localhost:55495, не production. Браузерные числа синтетические. Полные receipts и screenshots: `deploy-evidence/executive-priorities-20260915` в родительском workspace; итоговый source handoff фиксирует окончательные checks/commit.
