## Контекст

До этого среза режим доступа пользователя и приглашения выводился косвенно:
пустой список клубов означал всю сеть. Такая модель не отличает намеренный
`NETWORK` от отсутствующей, потерянной или ещё не классифицированной записи и
поэтому может расширить права при ошибке данных.

Для открытого теста необходима двухмерная авторизация:

- capability отвечает на вопрос «что разрешено делать»;
- AccessScope отвечает на вопрос «с данными каких клубов»;
- TenantExecutionPolicy отвечает на вопрос «разрешена ли операция для tenant
  сейчас», например с учётом suspension, canary или kill switch.

Ни роль, ни capability, ни entitlement не могут расширить AccessScope.

## Решение

1. У `User` и `UserInvite` хранится явный persisted mode:
   `NETWORK | STORES`.
2. `NETWORK` означает все текущие и будущие клубы только собственного tenant.
3. `STORES` означает точный allow-list в `UserStoreAccess` или invite scope.
   Пустой allow-list никогда не означает всю сеть. В expand-схеме он может
   существовать как quarantine, но runtime v1 отклоняет такой аккаунт при
   аутентификации.
4. Отсутствующий, неизвестный или противоречивый mode означает deny.
5. API перечитывает mode и связи с клубами из PostgreSQL при каждом
   аутентифицированном запросе. Store ID из JWT не является authority.
6. Изменение scope начинает действовать без повторного входа.
7. Связь user–store обязана быть same-tenant и защищается как application, так и
   database invariant.
8. Клиентские `tenantId`, `storeId`, `storeIds`, filters и UUID могут только
   сузить уже вычисленный доступ.
9. Platform Admin не получает неявный tenant-data bypass. Поддержка tenant
   выполняется только через отдельный, ограниченный и аудируемый support context.
10. Тот же контракт обязателен для HTTP, BFF, export, files, SSE/WebSocket,
    scheduler и background jobs.

## Рассмотренные альтернативы

### Пустой список означает NETWORK

Отклонено: ошибка загрузки, неполная миграция или удаление связей расширяет
доступ вместо его закрытия.

### Хранить scope только в JWT

Отклонено: отзыв клуба или понижение прав действует только после истечения
токена и создаёт несколько конкурирующих источников истины.

### Ограничиваться tenant isolation

Отклонено: пользователь одного клуба получил бы данные остальных клубов сети.

### Проверять scope отдельно в каждом controller/service

Отклонено: правила расходятся между list/detail/export/background surfaces.
Используется один `AccessScopeService`, а модульная интеграция фиксируется в
матрице.

## Последствия

- Создание и изменение пользователя/приглашения требует явного mode.
- Миграция проходит фазами; существующие аккаунты без store rows требуют
  классификации, а не автоматического повышения до NETWORK.
- Все модули первого пилота должны пройти отдельную инвентаризацию и тесты.
- Агрегаты считаются после ограничения исходных rows.
- Ошибка scope приводит к 401/403/404 по контракту, но никогда к расширенному
  набору данных.
