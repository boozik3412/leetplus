# Langame: частичная ручная синхронизация

## Текущее поведение (30.09.2026): «нет доступа» — не сбой

Разделы делятся на два вида отказов (`langame-section-limits.ts`):

- **Ограничение ключа или провайдера** — Langame не даёт этот раздел сети:
  `No permissions`/401/403, либо Langame больше не отдаёт раздел списком по
  всей сети (с 29.09.2026 `/guests/logs` без `guest_id` отвечает
  `400 … "field":"guest_id"`). Раздел показывается как «нет доступа по ключу
  API», а импорт остальных разделов считается **полным**: источник `SUCCESS`,
  задание `SUCCESS` с пометкой `LANGAME_SYNC_LIMITED: …`, курсоры
  `lastSyncedAt`/`lastSyncedDate` и daily coverage продвигаются, зависимые
  снимки строятся. Если нет доступа к продажам или выручке, `lastSyncedDate`
  не продвигается, чтобы после выдачи прав период догрузился.
- **Неполное чтение** — сбой транспорта/провайдера или отказ на второй и
  следующей странице раздела, который уже отдал данные. Это по-прежнему
  `PARTIAL` без продвижения курсора, как описано ниже.

Если ни один раздел не загрузился, источник остаётся `FAILED`.

Ежедневная синхронизация работает и для внешних сетей (PILOT/BETA/LIVE) с
подключённым Langame: после основной сети ночной воркер по очереди
синхронизирует каждую из них (сбой одной не останавливает остальные).
Нужен только доступ сети к модулям на запись (как для ручной загрузки из
/sync) и открытый срок доступа; OUTBOUND не требуется. Подробнее — раздел
«Ежедневная синхронизация внешних сетей» в
[runtime-security-contours.md](../security/runtime-security-contours.md).

Разделы ниже описывают историю; их утверждения о `PARTIAL` при отказе прав
заменены правилами выше.

## Уточнение требований и source follow-up, 27.09.2026

Для EZ GAME подтверждено владельцем: доступа к категориям и клубной
конфигурации сейчас нет. Основной режим — загружать все доступные разделы
при этих ограничениях. Получение дополнительных прав не является условием
работы товаров, остатков, продаж, выручки, гостей, сессий и транзакций.
Отказ отдельного provider read не прерывает независимые ручные разделы;
сохранённые данные недоступного раздела не удаляются. Отсутствие ответа не
становится подтверждённым нулём или доказанной полнотой периода.

Source follow-up сохраняет существующую MANUAL обработку и закрепляет её
гостевыми denial-, multi-club- и pagination-сценариями. Guest foundation сохраняет результат
как PARTIAL при неполных provider reads, а полный отказ всех reads — FAILED.
Это текстовый статус существующей таблицы, без миграции. Полный cursor не
продвигается; partial результат не закрывает complete daily coverage или
зависимые snapshots. Provider-ошибки выводятся безопасными сообщениями.
Интерфейс также трактует исторический guest run с `endpointErrors` как PARTIAL
в сводке, диагностике и истории. Пятиминутное ожидание браузера не обнуляет
статус продолжающегося server run: при открытой
странице отдельный observer получает существующий статус до завершения и не
отправляет новый start. Ошибка status GET показывается отдельно и сохраняет
последние известные сведения. Freshness и полнота остаются разными признаками.

Это source/local-fixture изменение. Оно не активирует external daily sync,
не меняет таймеры, credentials, provider egress, tenant/Store admission, схему БД
или production runtime. Регулярный внешний worker и отдельные курсоры
разделов требуют следующего scoped implementation и собственной приёмки.

## Пользовательский результат

Ручная загрузка проверяет и обрабатывает отдельно товары, категории,
клубные настройки/цены, остатки, продажи и выручку. Отказ Langame по одному
разделу не мешает загрузить остальные доступные разделы. Например, отказ
`/master_api/products/groups/active` не отменяет импорт `/products/list`.
Категории и конфигурация проверяются независимо: доступ к одному методу не
является доказательством доступа ко второму. Недоступный раздел не подменяется
успешным пустым ответом, чужими данными или другим API-ключом.

Результат содержит счётчики и, при неполной загрузке, `sourceResults[].steps`:
раздел, SUCCESS/FAILED, комментарий, опциональный clubId и количество строк.
Интерфейс показывает доступные данные и причины неполного результата сразу
после запуска и сохраняет комментарии в истории. Только полный успех имеет
зелёный результат; PARTIAL не называется исключительно «ошибкой аудита».
Raw provider body, API-ключи и параметры URL в новых комментариях не выводятся.

## Сохранность и полнота данных

- Ошибки обрабатываются только на границе provider read. Ошибка БД, целостности
  или tenant/source/Store admission останавливает источник как FAILED.
- После успешного чтения сохраняется соответствующий раздел; отказ категорий
  не архивирует ранее сохранённые категории. Аналогично сохраняются прежние
  товары/конфигурация при недоступности их метода.
- Остатки пишутся только для известных товаров; пропущенные из-за отсутствия
  каталога позиции явно отмечаются как неполная загрузка.
- Продажи, записанные до ошибки следующей страницы, сохраняются и учитываются
  в счётчиках. Последующий штатный повтор использует прежние idempotent upsert
  keys; полный курсор периода при частичном чтении не продвигается.
- Выручка заменяется только после чтения всех запрошенных date chunks.
  Если следующий chunk не загрузился, прежние факты выручки не удаляются.
- Если ни один раздел данных не завершён и нет сохранённых строк,
  источник остаётся FAILED. Само получение списка клубов не делает импорт PARTIAL.

CURRENT191 enum `IntegrationSyncStatus` содержит только SUCCESS/FAILED.
Миграция схемы не требуется: неполный provider job хранится как FAILED с
префиксом `LANGAME_SYNC_PARTIAL:` и читаемыми комментариями в errorMessage.
Settings API проецирует только такую явную запись в PARTIAL. Поэтому существующие
проверки полноты, выбирающие SUCCESS, не принимают частичную загрузку за полную.
`lastSyncedAt` и `lastSyncedDate` источника при provider failure не обновляются.
Legacy «факты сохранены, файл аудита не записан» сохраняет прежнюю семантику.

## Границы полномочий

Ручной импорт продолжает доступные разделы при любом provider-read отказе.
AUTO/ежедневный worker продолжает их при известном permission denial, но
не объявляет partial результат полным: coverage остаётся неполным, а
зависимые снимки блокируются. Неизвестные ошибки AUTO остаются fail-closed.
Внешние PILOT/BETA/LIVE сети по-прежнему требуют persisted exact Store binding
и свежую проверку клубов перед записью. Недоступность этого списка для внешнего
tenant блокирует admission целиком, а не расширяет scope. INTERNAL timers,
ключи и неподтверждённые клубы не используются для обхода ошибки внешней сети.

## Проверка и выпуск после переноса

Regression coverage: недоступные категории/цены с успешными товарами,
недоступный каталог без архивирования старых данных, все методы недоступны,
разный доступ клубов, неполная пагинация продаж, ошибка позднего revenue chunk,
неизвестные товары в остатках, DB failure, AUTO failure и успешный повтор.
Settings/UI отдельно проверяют PARTIAL, FAILED, старый audit-only PARTIAL и
отсутствие ложного success banner.

Compose generation3/activeblue, sole primary на `192.168.1.137` / `188.234.220.76`.

Его БД и старые app/worker units нельзя запускать ради этого исправления.
