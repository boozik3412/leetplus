# Assortment implementation context

Read for assortment, inventory or report changes. This guide preserves the source
contracts formerly in root AGENTS.md; verify the affected implementation when changing it.
File paths below are repository-relative. Current checks are in [verification](verification.md).
The [metric contract](../assortment-dashboard-metric-contract.md) and root security
invariants remain mandatory for their scope. Test ports and past receipts are history.


- Входы — защищённые CSV imports товаров, остатков, продаж и движений, а также сохранённые интеграционные факты; они заполняют каталог, `InventorySnapshot`, `SalesFact`, `StockMovement`, покрытие и конфигурации цен.
- Обычный INTERNAL daily обновляет inventory ежедневно даже при закрытом QUICK; только недавний повтор подавляется при success AUTO INVENTORY всех активных доменов за 1 час. Это не порог качества данных: freshness остаётся 36 часов. Inventory-only run не двигает sales cursor.
- `resolveGuestSessionStore` доказывает Store по полной топологии tenant; вызывающий код затем применяет permissions. Inferred binding не меняет historical timestamps или parser timezone.
- Общие точки реализации — `apps/api/src/common/assortment-health.ts`, `assortment-health-loader.service.ts` и `guest-session-store.ts`; loader строит доказанные store×product grains и передаёт факты в pure `buildAssortmentHealth`.
- Устойчивые границы engine: `AssortmentHealth`/`AssortmentHealthRow` и `AssortmentMetric<T>` с `value|null`, `state`, `reason`, `coverage`, `asOf`; денежные оценки дополнительно несут `basis`.
- Отсутствующие данные остаются `null`/`UNKNOWN`, известный ноль остаётся нулём, а `PARTIAL` не становится точным итогом; Web показывает причину и coverage у конкретной карточки.
- Cutoff запроса — `selectedAssortmentAsOf`/report `asOf`; `inventory.asOf` — отдельная дата наблюдения остатка и не переносится как cutoff.
- `DashboardService` добавляет summary в `GET /dashboard/summary`, а `ReportsService` использует те же row sets для `operations`, `inventory-turnover` и `replenishment` вместе с scoped rows и write-off details.
- `/assortment/dashboard` (`DashboardService.getSummary`) buckets period facts by the club-local day via `common/club-time.ts` (`onClubDays`: wall-clock shift + ±14 h query margin; freshness uses the stored instant via `source`). Rolling "last N days" windows (demand, active SKU, `AssortmentHealthLoaderService`, reports) still use UTC days.
- Web transport находится в `apps/web/src/lib/dashboard-summary.ts` и `apps/web/src/lib/reports.ts`; `/assortment/dashboard`, `/reports` и table pages сохраняют `from`, `to`, repeated `storeIds`/`categoryIds`, `asOf`, `noSalesDays` и subset URL.
- Карточки ассортимента кликабельны: OOS/low-stock/no-sales ведут в «Заказ товаров», turnover/excess и «Деньги в риске» — в «Деньги в остатке», а списания — в movement table с `subset=write-offs`.
- OOS `grossProfitAtRisk` хранит дневную/периодную оценку и cost basis: известная себестоимость позволяет расчёт, sale-price valuation не становится cost, отсутствие подтверждения остаётся null.
- Источник и production proof определяются canonical deployment documentation, а не веткой или наличием исходного кода.
- «Заказ товаров» (`/products/order`, `GET /reports/order-planning`, pure расчёт в `apps/api/src/reports/order-planning.ts`) — отдельный от `AssortmentHealth` сводный отчёт: продажи по дням клуба за 21–60 дней, дни в наличии по ежедневным `InventorySnapshot`, спрос = продано ÷ дней в наличии, заказ = спрос × дни запаса − остаток с кратностью поставщика. Строки — только store×SKU, которые были на остатке в окне или есть сейчас; услуги и OOS-исключения не показываются. Фильтры, сортировка и группировка по сети работают на клиенте.
- Этап 2 (30.10): старые отчёты-дубли стали редиректами на виды «Заказ товаров» с теми же `storeIds`/`categoryIds` (`orderPlanningHref` в `apps/web/src/lib/order-planning-views.ts`): `/reports/replenishment/table` → `view=order`, `/reports/oos/table` → `running-out`, `/reports/no-sales/table` → `no-movement` (+`noSalesDays`), `/products/movement/table` → `movement` (кроме `subset=write-offs`, который остаётся страницей списаний). `/products/order` принимает `storeIds`, `categoryIds`, `category` (имя) и `noSalesDays` как начальные фильтры. ABC и ТОП SKU — одна таблица `/reports/abc/table` («Рейтинг SKU и ABC»), `/reports/top-sku/table` редиректит туда. На `/reports` вместо блоков OOS, «Товары без продаж», «Остатки и потребность» и «ТОП SKU» — ссылки на виды «Заказ товаров».
- «Деньги в остатке» (`/products/stock-value`, 06.11): экран на тех же строках `GET /reports/order-planning` (по умолчанию окно 30 дней), расчёт в pure `apps/web/src/lib/stock-value.ts` (тесты `pnpm --filter web test:assortment`). Деньги = остаток × закупочная цена клуба (иначе товара); без цены — не в суммах, считаются отдельно. Виды: `frozen` (на остатке, не продавался ≥ `noSalesDays` полных дней клуба), `excess` (остаток − продаж в день × 14/30/60 дн.), `lost-profit` (продаётся, остатка нет: продаж в день × (выручка ÷ продано − закупка)), `all`; разрез по товарам, клубам, категориям, поставщикам. `/reports/assortment-risk/table` → `view=frozen` (+`noSalesDays`), `/reports/inventory-turnover/table` → `excess` при `excess=true`, `frozen` при `noSalesDays`, иначе `all` (`stockValueHref`). API `inventory-turnover` и `buildAssortmentRiskSummary` остаются для коммерческого аудита. Общие части таблиц — `components/report-table-kit.tsx` и `lib/report-table-format.ts`.
- «Рейтинг SKU и ABC» (`/reports/abc/table`, 13.11): группы приходят из `GET /reports/sku-performance` (накопленная доля до строки < 80% → A, < 95% → B, иначе C; отдельно по выручке и по валовой прибыли). Экран раскладывает строки в pure `apps/web/src/lib/abc-rating.ts`: пояснение «Как читать этот отчёт» с кривой Парето, по умолчанию матрица 3×3 «выручка × прибыль» (`?cell=AC` — открытая клетка, клетки с расхождением выручки и прибыли подсвечены), «Таблица» по кнопке (`?view=table`, CSV). Товар с продажами и `cost = 0` помечается «нет закупки»: его прибыль равна выручке. Фильтр поставщика скрыт, пока ни у одного товара нет поставщика.
