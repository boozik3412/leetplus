# Эффект игры: по сети, клубам, сценариям и гостю

Дата контракта: 14.10.2026. Прочитайте этот документ перед тем, как менять:
- вкладку «Геймификация → Эффект»;
- блок «Эффект игры для гостя» в карточке гостя;
- контрольную группу (holdout) заданий и кейсов;
- выгрузку обзора геймификации.

## Данные

Данные считаются по дням в часовом поясе сети (`networkTimeZone`) с учётом каждого клуба.

| Метрика | Источник |
| --- | --- |
| Дни визитов, сессии, часы | `GuestSession`: старт сессии. Длительность ограничена 24 ч. |
| Списания с депозита | `GuestTransaction` с `amount < 0`, см. `common/guest-transaction-money.ts`. Суммы больше 20 000 ₽ не учитываются. |
| Бар | `SalesFact` без отмен. |
| Деньги гостя | Списания + бар. Эти источники не пересекаются. |
| Клуб гостя | Клуб, где у гостя больше всего дней активности: сессии, списания или покупки. У части сессий общего домена нет `storeId`, но у транзакций и продаж он есть. |
| Стоимость | `GuestGameReward` в статусе PAID. Бонусы и деньги считаются по номиналу. Призы считаются штуками, без цены. |

Профили сотрудников (`isStaffTest`) не входят ни в участников, ни в сравнение. Профили без `guestId` не измеряются, их количество показывается в `dataQuality`.

## Метод

- **Окно.** День старта `d` — это активация игры или первая награда сценария. «До» — 28 дней перед `d`, «после» — 28 дней после `d`. Сам день `d` не входит ни в одно окно. В отчёт попадают только участники, у которых окно уже закончилось.
- **Сравнение.** Это гости, которые были в клубе в день `d` и до конца окна не начали участвовать. Расчёт по активации берёт гостей вне игры, расчёт по сценарию — игроков вне сценария. Сравниваемый гость попадает в ту же корзину по визитам «до»: 0, 1, 2–3, 4–7, 8–14 или 15+. Если таких гостей меньше трёх, поиск расширяется на ±1…3 дня, и каждый гость измеряется вокруг своего дня визита. Ограничения сценария по клубам (`storeIds`) применяются и к сравнению.
- **Эффект на гостя.** Изменение участника минус среднее изменение похожих гостей (difference in differences). Интервал 95 % считается нормальным приближением при выборке от 10 гостей.
- **Вывод.** Решают деньги; если по деньгам вывода нет, решают дни визитов: больше визитов при оценке денег ниже нуля — отдельный вывод «Чаще ходят, не больше тратят» (`VISITS_ONLY`). «В пределах случайности» означает, что интервал включает ноль; это не доказательство нулевого эффекта.
- **Эффект для гостя.** В карточке гостя тот же расчёт, но для одного человека. Пока 28 дней не прошли, окно сжимается до прошедших дней, минимум 7. В интерфейсе прямо сказано, что один гость — это не статистика.
- **Ограничение.** Участники сценариев сами выбирают, участвовать или нет. Сравнение убирает разницу в частоте визитов, но не в мотивации. Причинный ответ даёт только контрольная группа.

## Контрольная группа (holdout)

- **Где включается.** `holdoutPercent` (0–50) и `holdoutStartedAt` есть у `GuestGameMission` и `GuestGameLootBox` (миграция 194). Для кейсов работает только `STANDALONE`, потому что кейс-награду выдаёт задание. У Battle Pass контрольной группы нет.
- **Кто попадает.** Разбивка детерминированная: `isInGameHoldout` (FNV-1a от `scenarioId:profileId`, бакеты 0–9999). Если увеличить процент, в группу только добавятся гости. Любая смена процента начинает разбивку заново (`setHoldout`), потому что результаты разных разбивок нельзя складывать.
- **Как применяется.** Живой движок правил (`appendDryRunHoldoutCheck` рядом с проверкой аудитории) не выдаёт задание и кейс гостю из группы. Портал (`guestPortalInHoldout`) их не показывает. Кейс, который уже лежит у гостя, остаётся доступным.
- **Как измеряется.** Сравниваются все активированные игроки в охвате сценария: назначенные против контрольной группы (intent to treat). Для каждого считается 28 дней до и после `max(старт разбивки, активация)`. Результат появляется через 7 дней.
